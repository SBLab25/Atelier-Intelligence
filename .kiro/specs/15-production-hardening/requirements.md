# Spec 15 — Production Hardening: Requirements

Source: `kiro_upgrade_prompts.md`, Prompt 14 ("Prepare CJI for a controlled production release"). Builds on Specs
01–14: typed settings with per-role checks (04), repositories (05), collector hardening with readiness (07), LLM and
MCP gateway with audit records and per-run budgets (08), durable workflow with resume (09), packaging (11), `/api/v1`
with tokens, roles and rate limits (12), Next.js with session cookies and bundle scan (13), feature parity (14).

**Status:** Implemented 2026-10-29 (approved: "implement spec 15", decisions OD-158 to OD-177 as written). Final gate rerun: every phase passed; release check NOT READY (6 blocked, 0 failed). Record, gate findings G-1 to G-16 and deviations D-1 to D-17 in `tasks.md`.

The prompt asks to implement **and verify** twelve controls, isolate development-only defaults, prove that no
sensitive data reaches logs, reports or client bundles, document operational limits and AI budgets, and never claim
readiness for an unverified control. Its acceptance criteria: the release checklist is executable, failed checks have
owners and blockers, and rollback is tested.

**Release target assumed here (OD-158):** one host, run by the project owner, with `cji-api`, `cji-collector`, the
five MCP servers, the Next.js server and (optionally) Streamlit as separate processes behind a TLS reverse proxy, and
PostgreSQL on Supabase. No containers, no second instance of any service.

## 3. Requirements

1. **R1 Logs:** every Python service and the Next.js server can write JSON log lines with `request_id`, `run_id` and
   `trace_id`; a request through Next.js, the API, a run and its MCP calls can be followed by one id.
2. **R2 Metrics and traces:** the API and collector expose the OD-160 series; `cji-trace show` prints the span tree
   of one request across processes.
3. **R3 Audit:** every OD-162 action writes one allow-listed security record; no record contains a secret, a token, a
   comment or a client address.
4. **R4 Secrets:** every secret in the inventory has a rotation procedure; API token, session key, cursor key and
   tracker key rotation are tested end to end.
5. **R5 Scanning:** dependency and secret scans run in CI and the gate; findings fail the run unless the checklist
   records an accepted exception; container scanning is reported `n/a` with owner.
6. **R6 Abuse controls:** sign-in limits apply per real client; failed authentication is limited; all limits are
   documented with their scope.
7. **R7 Backup and restore:** a backup of a populated pgserver deployment restores into an empty one with equal row
   counts, table checksums and file hashes.
8. **R8 Migrations:** `up`, `down` and `up` again succeed on a populated database; the previous release runs on the
   rolled-back schema; readiness reports a schema that is behind.
9. **R9 Health:** every service has liveness and readiness; `cji-ops status` reports all of them.
10. **R10 Recovery:** the seven OD-169 cases pass and their observed behaviour is recorded.
11. **R11 CI:** `ci/run_ci.py` runs every stage locally with ratchets and exits non-zero on failure.
12. **R12 Deployment:** `docs/deployment.md` exists; `cji-settings check --role production` and the frontend env check
    reject each violated rule (one test per rule).
13. **R13 Development defaults:** production settings activate none of the inventory's development behaviour; a new
    ungated branch fails a test.
14. **R14 Sensitive data:** the canary scan finds no secret marker in any output and user markers only where allowed.
15. **R15 Limits and budgets:** `docs/operations.md` lists every limit and the AI budgets, checked against the settings
    model by a test (no undocumented setting, no documented setting that does not exist).
16. **R16 Release checklist:** `ci/release_check.py` runs, prints every control with result, owner and blocker, and
    says READY only when nothing is failed or blocked.
17. **R17 Rollback:** the OD-175 drill runs in the gate and its results are recorded.
18. **R18 No regressions:** the Python suite, Vitest, Playwright fixture and live phases, parity check (Spec 14) and the
    static-check ratchets pass; Streamlit and the CLI behave as before apart from OD-177's additions.

## 5. Out of scope

Containers and orchestration; multiple instances and shared rate limiting; OpenTelemetry export; a secrets vault;
daily or monthly LLM ceilings; OIDC or per-user identity; hosted CI; applying anything to the real Supabase database;
the Spec 14 carry-overs (F-76, F-78, F-79, F-49, run paging), which stay with their owners.
